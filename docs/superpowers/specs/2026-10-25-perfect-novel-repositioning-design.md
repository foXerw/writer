# 「完美小说」重新定位设计文档

日期：2026-10-25 ｜ 状态：待发起人终批 ｜ 前身讨论：本仓 UI 气质改造 + 设定图谱/AI 功能规划脑暴（已过一轮 builder-check，8 项疑问全部处置：5 项设计侧拍板，3 项发起人回答）

## 1. 意图与动机

把本项目从"VSCode 风格的小说文本编辑器"重新定位为**"有 AI 共著能力的小说创作工作台"**。

核心信念：烂尾病（伏笔埋了忘收、地图切换拖沓、配角扁平、正反派动机不清、力量体系不自洽——例如主角有熟练度系统却没人交代普通人怎么修炼）不是写作能力问题，而是**设定缺乏系统化管理**的问题。解法是给每本书建一份结构化、AI 可理解的"设定数据基石"，让 AI 基于它做整理、补全与审阅。

- 用户定位：开源工具，服务所有普通写作者；发起人本人是第一用户（dogfooding）。
- 成功验收画面：作者用它写完两章 → 触发 AI 整理 → 角色卡与图谱"刷新"（走差异确认）→ 看到 AI 的章节检视意见。

## 2. 优先级与总体决策

- 功能优先级（发起人明确）：**设定图谱 > AI 实时补全 > 章节审阅**；在此之上先做 **UI 重构**。
- 代码仓决策：**演进式重构，不推翻重做**。依据体检报告：Electron 主进程壳、主题系统（CSS 变量 + antd 双 token + Monaco 双主题 + 防闪屏）、导出管线（docx/epub/pdf）、纯函数服务是健康可复用资产；真正缺的是关系型数据模型、集中数据访问层、编辑器扩展接缝——这三者不存在于新旧任何一版代码中，属于新建而非重写。
- 仓库更名：改为"完美小说"（GitHub 仓库改名后旧地址自动跳转；包名等英文标识用 `perfect-novel`，App 显示名"完美小说"）。**时机拍板：M1 顺手完成**——Electron 的 userData 目录名派生自产品名，越晚改名，theme.json/窗口状态/API key 等要二次搬家；发起人确认当前无外部用户，无需保旧目录升级路径（仍做一次搬运以防发起人本机数据丢失）。

## 3. 目标

- G1 数据基石：统一的"实体-关系-事件"模型，每本书一个纯文件数据目录，人可读可改、Git 可管、AI 可解析。
- G2 图谱视图：世界观、角色成长、剧情走向、关键选项、人物/任务关系——**五种视图是同一张数据网上的五个筛选/聚合，不做五套数据**。
- G3 AI 自动维护闭环：AI 读章节 → 抽取新实体/关系/伏笔变更 → 生成差异提案 → 作者确认/驳回 → 落盘（带"出自第几章+原文引用"溯源）。
- G4 AI 实时补全：类代码补全体验（ghost text，Tab 采纳），上下文携带设定数据。
- G5 章节审阅：AI 以读者视角出结构化意见（节奏、人物扁平点、动机/设定冲突、伏笔未回收对账），锚定到段落。
- G6 UI 气质改造：正文排版（衬线、行高、每行字数、纸感）、专注模式、补全 spacing/typography/radius 设计 token（当前只有颜色 token），为图谱视图留布局位。
- G7 Token 用量统计：按功能（补全/审阅/图谱整理）分账，界面上可查"这本书至今让 AI 花了多少"。**不设独立里程碑：账本内置在 M4 建的 AI 服务层里，M5/M6 上线时天然继承。**
- G8 仓库/产品更名落地。

## 4. 非目标

- 多用户协作、云同步、账号体系。
- 内置 AI 服务/代充额度——只做 BYOK（用户自带 key）。
- 移动端、Web 版。
- 发布/连载平台对接、精排版印刷流程（现有导出复用即可）。
- 自动续写整章的一键生成——AI 是副驾驶，不是代笔。

## 5. 反目标（技术上跑通也算失败）

- 作者被迫手动维护大量关系表——"填表填到弃书"。基础人设（人物卡等）是人写的，**演化数据必须靠 AI 整理 + 人确认差异**。
- AI 写入的数据无法溯源、不可撤销。
- 长到百万字后功能失效或上下文失控（任何请求不得"全量读全书"）。
- 为赶新功能堆第 N 个 god component，债越还越多。

## 6. 约束与技术选型（已定）

- 栈沿用：Electron + electron-vite + React 18 + TypeScript + Zustand + antd 5 + Monaco（直接 monaco-editor，不用 @monaco-editor/react，顺带清理该未用依赖）。
- AI 接入：**双协议 adapter**——设置里选协议类型，支持 (a) OpenAI 兼容（Base URL + Key + 模型名，DeepSeek / 通义 / OpenRouter / 本地 Ollama 皆可）与 (b) Anthropic 原生（官方 key 直连 Claude；官方 OpenAI 兼容层能力受限且不承诺稳定，故不做单协议方案）——发起人拍板。定位"最高质量优先，不设用量预算"，但配合分层上下文（见 7.4）。
- 模型配置 schema：按功能（补全/整理/审阅）各留独立配置槽位（补全可单配快模型），**MVP 界面只暴露一套默认 + 可选覆盖**——设计侧拍板。
- Key 存储：存 userData 目录配置文件（与 theme.json 同级同待遇），**不引入 OS 钥匙串**——发起人拍板，对齐市面 AI 工具惯例。
- 数据目录纯文件明文，格式规范写进公开文档，允许第三方 AI 工具（如 Claude Code）直接操作一本书的数据。
- 图谱渲染库选型倾向 xyflow（React Flow）——我的建议，实现者可在同层抽象下换。

## 7. 设计展开

### 7.1 数据目录（基石，一切的前提）

每本书一个文件夹，建议结构（字段级 schema 留给实现）：

```
<book>/
  book.json                 # 书名/类型/简介/力量体系说明等元信息
  chapters/NNN-标题.md       # 正文（沿用现有），front-matter 记章节 id/卷
  world/<分类>/<条目>.yaml    # 世界观设定条目（含力量体系、地理、组织…）
  characters/<id>.yaml       # 人物卡：基本信息、性格、目标动机、成长弧线、
                             #   关系列表（按 id 引用！）、持有设定链接
  plotlines/<id>.yaml        # 剧情线：阶段里程碑序列、关联角色/设定/章节
  choices/<id>.yaml          # 关键选项/抉择节点：触发的章节、分支后果
  foreshadow.yaml            # 伏笔台账：埋设章节、计划回收章节、状态
  .ai/summaries/chapters/NNN.yaml   # 章节摘要（AI 沉淀）
  .ai/summaries/volumes/…           # 卷梗概（滚动凝缩）+ 全书大纲线
  .ai/proposals/*.yaml       # 待确认的差异提案（含溯源引用）
```

关键规则：
- 所有跨实体引用一律用稳定 id（uuid 或 slug），改名不断链（修复现状"关系存角色名、设定按文件名前 8 位匹配"的断链病）。
- 章节 id 与文件名解耦（现状 order/标题都编码在文件名里，是字符串手术重灾区）。
- **"卷"是一等公民**：章节树按卷分组，支持建卷/改名/排序；卷同时是 AI 摘要凝缩的天然单位——设计侧拍板。
- 迁移契约（发起人确认：无存量稿、无外部用户，可硬切）：打开旧格式项目时**就地自动迁移**（先把旧文件整体备份到 `<book>/.migration-backup/` 再改写），不做新旧格式双轨长期并存；迁移失败回滚到备份并明确报错。一次性脚本形态留给实现。
- 外部并发修改（发起人工作流里 Claude Code 常直接改书目录文件）：M2 的数据访问层必须是**单一入口 + 可失效缓存**，并加文件监听——外部改动落盘后图谱/角色卡等展示自动刷新；若应用内存中有未保存编辑与磁盘变更冲突，弹出警告让用户选择"保留我的/重新加载"，**不做自动合并**——设计侧拍板的最小契约。
- 存量老书批量回填（整本历史章节一次性整理）：**不进 MVP**；对导入旧书的未来用户是刚需，列为 M6 后的扩展项（需要任务队列/进度/可中断，形态届时另设计）。

### 7.2 统一"实体-关系-事件"模型

实体（角色/设定/地点/物品/势力/剧情线/伏笔）为节点；关系为带类型、带生效章节的边；事件（章节里发生了什么）把三者挂回正文。五种图谱视图 = 对这张网的五种查询：世界观（分类过滤）、角色成长（单角色时间轴 + 弧线阶段）、剧情走向（plotline 里程碑链）、关键选项（choice 节点及其后果边）、人物/任务关系（关系边图）。

**schema 一次设计到位、UI 分步点亮**（发起人确认）：M2 的数据模型即包含全部五类实体与关系，杜绝后补迁移；但剧情线/关键选项/伏笔的**录入 UI 推迟到 M4 之后**——这些数据主要由 AI 整理产生，避免在 AI 闭环上线前把作者推回"手填关系表"的反目标。

### 7.3 AI 维护闭环（"图书管理员"）

触发：章节保存后手动点"整理本章"（MVP 阶段先手动，防打扰）。流程：AI 读 [本章全文 + 出场实体卡 + 伏笔台账] → 产出结构化差异提案（新增实体/更新字段/新关系/伏笔状态变化）→ 提案落 `.ai/proposals/` → 图谱侧以"待确认"徽章提示 → 作者逐项看差异、采纳/驳回/修改 → 采纳才写正式文件。每条 AI 生成数据带溯源（章节 id + 原文引用），可撤回重跑。

### 7.4 分层上下文与检索

任何 AI 请求的上下文组装上限策略：全书大纲线 + 当前卷梗概 + 最近 N 章摘要 + 当前章前后文 + 涉事实体卡（按实体-章节索引精确捞取），绝不全量读正文。章节索引（哪个角色/设定/伏笔出现在哪章）由整理闭环顺手维护。

### 7.5 实时补全

Monaco 侧接 InlineCompletions API（ghost text）；触发为停顿/快捷键；prompt 按 7.4 组装，明确带人物口吻与设定约束；采纳/忽略行为可做简单偏好沉淀。审阅（G5）同理是"选择范围 → 结构化意见面板"，意见锚定段落、可一键转为伏笔台账/设定的修订提案。

### 7.6 UI 气质改造（先行动工，不依赖数据基石）

- 设计 token 补齐：spacing/typography/radius 刻度，消灭 38 处 `!important` 与内联 `<style>` 注入的做法。
- 正文：衬线字体族、舒适行长行高、纸感背景；字数统计改中文正确口径（现状空白分词对中文无效）。
- 专注/打字机模式打磨；图谱作为第二视图的布局位（编辑器视图 ↔ 图谱视图切换）。
- 顺手还债（新功能前置而非可选）：Workspace 712 行 god component 拆分、双 IPC 门面（useIPC 类型化 vs ipcService 裸通道）合一、tab/最近项目双真源收敛、34 个存量 tsc 错误清零并把类型检查纳入 build、拆分 handlers.ts（813 行）。

## 9. 留给实现者的自由度

字段级 schema、图谱布局算法与交互细节、提案 diff 的具体格式、补全触发参数（停顿时长等）、prompt 工程、审阅意见的分类词典、迁移脚本形态——只要不违背第 5 节反目标与 7.4 上限策略。
